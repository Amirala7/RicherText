The product

The problem

People who write every day (consultants, PMs, lawyers, founders) choose between heavy suites that are slow and cluttered, and Markdown tools that are fast but make non-technical people learn syntax and paste badly into email. RicherText sits in the gap: it opens instantly, formats like a word processor, and gets out of the way.

Principles that broke ties

Never lose a keystroke

Data safety outranks every other editor concern. It decided autosave, the offline cache and the content format.

Fast beats featureful

Every feature has to justify its cost in load time and clutter. It's why images, tables and AI are out.

Small but complete

A narrow product that works end to end beats a broad one that half works: landing, payments and editor all ship.

Boring infrastructure

Managed, proven services for auth, payments and hosting, so the effort goes into the writing experience.

Who it's for

Individuals who write daily and pay for their own tools. They value speed, focus, reliability and clean output; they don't need collaboration, databases or templates. That one sentence removed most of the feature list.

Scope decisions

What's in, what's out, and why

In v1

  • Headings, bold, italic, underline, strike, lists, links, quotes
  • Text size, six text colours, writing font per document (Geist or IBM Plex Serif)
  • Undo / redo and keyboard shortcuts for everything
  • Autosave with a quiet "Saved" indicator; works offline
  • Clean copy and paste to and from Docs, Word, Outlook and Gmail
  • Free plan (one document, plain text), monthly and yearly subscriptions, Customer Portal
  • Light and dark, desktop and phone

Deliberately out

  • Collaboration, sharing and comments: not what this user needs
  • Images, tables and embeds: cost load time and clutter
  • Templates, AI and plugins: a different product
  • Full-text search: needs an external index; titles filter instead
  • Native apps: the web app works at phone width
  • Export: moved to next steps to ship the core first

Architecture

Few moving parts, one source of truth

The browser writes documents straight to Firestore, so its offline queue and retries protect every keystroke. Anything that must not be forged (creating documents, billing, the plan) goes through the server. Firestore is the only place that decides who has access.

Key technical decisions

DecisionWhyADR
Next.js on FirebaseOne framework for a static, indexable landing page and a gated app; Firebase gives auth, database, functions and hosting under one project.0001–2
FirestoreSecurity rules, an offline write queue and scale-to-zero match the principles; its weak spots (search, lock-in) don't matter here.0004
TiptapMature ProseMirror editor with MIT packages; one shared schema keeps paste, storage and rendering consistent.0006
Session cookiesThe client signs in; the server holds an httpOnly cookie and checks it in every layout, action and route, refreshed silently for active writers.0026
Hand-written webhookSignature-checked, idempotent (event IDs stored in the same transaction) and order-independent (re-reads Stripe), so retries and out-of-order events are safe.0027
Server-side create and deleteEnforces the Free limit with a counter in a transaction; a query there serialised every user (8 parallel creates took 12 s; with the counter, 20 take 30 ms).0028
Content as a JSON stringFirestore rejects maps nested deeper than 20 levels, so a list indented three times could never save. Found in an audit, fixed test-first.0033
Offline cache in IndexedDBEdits survive a reload or a dropped connection; shared by tabs and deleted on sign out.0029

Trade-offs

What I gave up, and why it was worth it

ChoseOverBecause
Browser writes to FirestoreSaving through our own APIFirestore's offline queue and retries for free; rules do the checking. Cost: business rules live partly in security rules, so they get their own test suite.
Whole document per saveSending only the editsSimple and robust for memos of 10–40 KB. Edit-step syncing is collaboration machinery we don't need.
One Firebase projectStaging plus productionLess to run for a demo. Cost: rules, webhook and deploy changes can't be rehearsed in the cloud first, so the emulators and the deploy checks carry that weight.
Local deploy scriptCI/CD and auto-deploys from GitHubEvery deploy runs the full suite from a clean main, with no extra service to secure. Cost: deploys depend on one machine.
Local first on the emulatorsBuilding against a real project from day oneNo cloud cost or secrets until the end, and fast, repeatable tests. Cost: production-only issues (regions, IAM, cleanup policies) surfaced at deploy time.
Stripe Portal for billingOur own billing screensLess code and fewer states. Cost: plan changes leave the app's design for a moment.
Scale to zeroAn always-on serverCosts nothing while idle, within a €5 budget. Cost: a few seconds' cold start after a quiet spell; the landing page is served from the CDN anyway.
Geist only, one accentA richer visual identityA calm, typographic product; fewer decisions per screen. The writing font is the one place with a choice.
Every trade-off was written down before building, with the options weighed, so the reasons survive longer than the conversation that made them.

How it was built

Test-first, decisions on paper, one design system

Tests first, then locked

Every change starts with a test that fails for the right reason. Existing tests can only change with explicit approval, so they hold the business rules in place.

Decision records

35 ADRs: context, options, decision, consequences. Superseded ones stay, so the history of a choice is readable.

Small vertical slices

Short-lived branches, conventional commits, merged only when lint, types and all tests pass in light, dark, desktop and phone.

What the tests cover

SuiteCountWhat it proves
Unit (Vitest)436Components, forms, autosave timing, paste clean-up, plan mapping, config guards, setup and deploy scripts
Emulator103Security rules (ownership, Free limit, read-only), webhook signatures and idempotency, deep nesting, no secrets in server logs
End to end (Playwright)176Every flow on desktop and phone: sign-up, checkout states, editor, offline, paste, landing without JavaScript, security headers, no secrets in the console

Security and privacy by default

  • No secrets in the repo; real values only in Secret Manager
  • Logs never carry tokens or personal data, checked by tests
  • A production build refuses to run without real config
  • Security headers on every response (no framing, HSTS)
  • Billing data is server-written only; users read only their own
  • Data and servers in the EU

Design system

Typography does the work

Large type and whitespace instead of graphics: no illustrations, no decorative elements. Landing page and editor share one atomic component set (tokens → atoms → molecules → organisms → templates), and nothing new appears on a screen until it's approved into the system.

Rules

  • Geist everywhere; the logotype is Geist set italic and stretched
  • One accent; colours only through theme tokens, in light and dark
  • Spacing on a 4px grid: 4, 8, 12, 16, 24, 32, 48
  • Soft radius: 5, 7 and 10px; flat surfaces
  • Never place elements of different heights side by side
  • Gaps inside a space are equal; edges one step larger
  • Nothing changes size on state change
